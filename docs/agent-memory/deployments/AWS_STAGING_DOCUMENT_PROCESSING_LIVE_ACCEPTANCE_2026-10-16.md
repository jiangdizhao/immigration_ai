## Incident and investigation timeline

1. **Initial live failure (2026-10-15/16):** two different PDF uploads, including an ordinary five-page Chrome Print-to-PDF document from the Department of Home Affairs, reached stored/clean state but extraction failed with `processingStatus=failed`, `errorCode=malformed_document`, zero units. Processing failures appeared in the UI as `Document cannot be processed in its current state.` HTTP 409 was a misleading result of catch/error translation.
2. **All-format investigation:** branch `audit/document-processing-all-formats-20261016`, commit `edc593fb8317d56f3aa7a94a3c322abf61703b2b`. In a local production `node:22-bookworm-slim` / Next.js standalone Docker image, `pdfjs-dist/legacy/build/pdf.mjs` was present but its dynamically loaded `pdf.worker.mjs` was absent; a valid synthetic PDF failed for this reason. The other eight non-image worker formats parsed correctly in that same image. JPEG and PNG did not have an in-container live Vision-provider test at audit time.
3. **Focused implementation:** branch `hotfix/document-processing-reliability-20261016`; commits:
   - `94bb397c617f57ead7706dfca4d106ffaff830af`: include PDF.js worker in Next standalone output tracing; classify missing dependency as `parser_dependency_unavailable` and unexpected parser failures as `parser_worker_failed`; preserve genuine `malformed_document`; distinguish HTTP 422 (invalid/limit), 503 (parser or storage/persistence unavailable), 504 (timeout), and 409 (true state conflict); preserve explicit `retryFailed` handling.
   - `4e339a0b7cb448257b4ec3074bf03c7b65cd0658`: add production-image all-format gate and upload-to-evidence regression test, strengthen actual PDF runtime verification, record performance evidence in `docs/agent-memory/audits/DOCUMENT_PROCESSING_HOTFIX_PERFORMANCE_2026_10_16.md`.
