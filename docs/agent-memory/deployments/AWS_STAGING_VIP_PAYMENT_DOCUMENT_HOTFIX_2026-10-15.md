## Change 1 — Stripe live invoice.paid VIP activation incident

- **Incident:** On 2026-10-15 AEDT, two real AUD 1.00 monthly subscription invoices were confirmed `paid` by Stripe, and `checkout.session.completed` received HTTP 200, but related `invoice.paid` deliveries returned HTTP 500 (`Webhook processing failed.`), leaving VIP activation unconfirmed.
- **Root cause verified:** CloudWatch at around 21:36 AEDT reported `TypeError: The "string" argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date` / `ERR_INVALID_ARG_TYPE`. The failure originated in `chatbot/lib/db/queries.ts` `applyVipInvoicePaid`: interpolating the JavaScript `Date` directly into raw Drizzle SQL bypassed timestamp encoding. This regression was introduced in commit `2830f59cc37b` on 2026-10-10 while preserving prepaid entitlement when settling recurring invoices.
- **Fix:** `rawPgTimestamp(currentPeriodEnd)` with explicit `::timestamp` SQL casts; existing `GREATEST(COALESCE(vipExpiresAt, paidPeriodEnd), paidPeriodEnd)` logic unchanged. The invoice payment marker, user entitlement projection, event completion, and notification insertion are atomic. Retry claims and paid-invoice idempotency guard are retained.
- **Pre-deployment validation reported by coding agent:** original SQL reproduced the exact Date serialization error against isolated PostgreSQL; replacement passed. 37 focused VIP/webhook/entitlement/real-PostgreSQL tests passed; no failures or skips. Original disposable isolated DB was removed after testing.
- **Post-deployment state, as last observed:** deploy of the fix is verified by owner CLI output, **but neither user's current VIP status nor any post-`:46` Stripe HTTP 200 `invoice.paid` delivery has yet been confirmed**. A subsequent Stripe screenshot displayed prior HTTP 500 delivery attempts and an automatic retry pending; `Resend` was disabled on an older attempt with the message `Only the most recent delivery attempt can be resent.` Do not equate historical 500s with a demonstrated failure of the new image. Do not claim paid customers are recovered until verified.
- **Required recovery:** inspect the most recent delivery attempt for each distinct paid `invoice.paid` event ID. Confirm a 200 on a retry after `:46`, or deliberately resend ONLY the latest attempt per event once safe. Match event/invoice/subscription identity, confirm `VipBillingEvent` processed, corresponding `VipSubscription.lastPaidInvoiceId`, and each user entitlement through authorized status/admin UI. Do not charge again, bulk-replay unrelated events, or patch memberships manually without tracing original verified invoices. If new HTTP 500 occurs, inspect matching new Chatbot CloudWatch logs.
