## 1. Executive finding

The repository has a real customer-owned Project foundation, Project-scoped customer membership, private Project Chats, customer-controlled Fact publication and AI-use grants, immutable-version Project documents, consent for importing a customer-owned Chat document into a Project, and exact-version document evidence processing. These are reusable integrity patterns. They do not authorize staff access.

The current Project schema and service authorize customers and their active customer members. Staff roles are global account labels used by separate lawyer-request, consultation, admin and AI-quality workflows. No Project staff assignment, professional credential verification, durable human Project message stream, Project service engagement, service contract/signature record, staff-attested service payment, customer-to-staff disclosure grant, or Project package review/approval was found in the inspected application schema, migrations, routes or services.

Existing LawyerClarificationRequest, ConsultationRequest, AnswerReview/ReviewArtifact and Stripe VIP billing solve different scopes. Reusing them as Project service contracts or approvals would conflate an answer-specific review, a scheduled consultation, AI feedback, or an AI subscription with a durable Project relationship.

**Accepted professional-review baseline (not implemented in the inspected application):** Phase 13 Roadmap §1.6 requires an identified authorized lawyer to review the exact version of each managed per-school application package and each Student 500 package (docs/agent-memory/PHASE13_STUDY_JOURNEY_ROADMAP.md:43). The roadmap separately assigns institutional submission to an authorized education representative (§1.8; line 45); that submission role does not replace lawyer review. Education-specific review may be additional. Changing the lawyer-review baseline requires a separately accepted architecture decision.

**M4 therefore needs an additive, explicitly scoped authorization and evidence layer.** At minimum, staff access must require current staff identity/authority, current Project assignment, exact resource ownership/scope, an active customer-to-staff disclosure for that data class, and current Project/resource/version state. M2 AI grants are an independent authority and must not satisfy the disclosure condition.

## 7. Search limits and unresolved decisions

Targeted local searches covered chatbot and legal-service application schema, migration SQL (not generated snapshots), Project/M2 modules, lawyer/consultation/review routes and billing code for proposed M4 entity families. The candidate names ProjectStaffAssignment, ProjectHumanThread/Message, ServiceEngagement, AgreementVersion, SignatureEvidence, CustomerDisclosureConsent, PaymentAttestation, Project professional review/approval and ProjectAuditEvent were not found as current Project capabilities. This does not verify integrations outside the repository.

**M4-002 assignment bootstrap boundary:** a global staff/admin role is not a Project assignment or access grant. Before any protected Project data is exposed, require explicit customer-owner authorization of the specific staff assignment and an actor permitted by a separately approved assignment-authority policy; then require the applicable resource/data-class authorization. Until M4-004 disclosure grants exist, protected resource reads remain fail-closed. Who may initiate or delegate assignment creation remains pending owner approval.

The following remain **PENDING PROFESSIONAL/OWNER REVIEW**, not approved policy:

1. Which services are legal advice, education-agent representation, administration or another service, and which credentials/licensing/registration must be verified for each.
2. Which staff roles may perform which action, whether principal/admin may see case data, and emergency access requirements.
3. Which Project data classes may be disclosed, to whom, for what purpose and how long; whether consent is recipient-specific, assignment-specific, class-wide, guardian-controlled or renewable.
4. Whether a customer member may authorize staff disclosure; proposed default is owner-only absent an accepted delegation model.
5. Whether/how customer Chat content, private member Chats, minors' data, identity documents, financial information, extracted facts and education records can be shared; retention, residency, access logs, deletion, legal hold and post-termination access.
6. Accepted contract form, execution/signature provider, identity proof, capacity/guardian signature, timestamps, revocation/cancellation/variation, enforceability and evidence retention.
7. Payment condition semantics, fee payer/payee, staff role allowed to verify, accepted proof, reversals/refunds/chargebacks, amount/currency/tax/accounting treatment and privacy.
8. How the accepted exact-version lawyer-review requirement is evidenced; conflicts, second approval, package completeness, source/currentness thresholds and which changes invalidate approval.
9. Whether education-specific review is additionally required, self-service versus managed-service disclosures, and customer/guardian authority. The lawyer-review baseline for both managed package types is fixed by the accepted roadmap unless a separate architecture decision changes it.
