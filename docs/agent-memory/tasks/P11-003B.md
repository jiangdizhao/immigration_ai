## Problem to solve

P11-003A correctly filters public items to `editorialStatus === "published"`.

But filtering inside code imported by client components is not a sufficient confidentiality/editorial boundary once real draft or review-required entries exist.

Future unpublished entries may contain:

- unreviewed AI summaries;
- incomplete source metadata;
- internal notes;
- draft lawyer commentary;
- unpublished legal interpretation.

Those records must not be sent to public client bundles.

The correct architecture is:

```text
repository editorial source
        |
        v
server-only registry / validation
        |
        +--> unpublished editorial records remain server-only
        |
        v
published public projection
        |
        v
public server route
        |
        v
client presentation/search/filter
```

## Required architecture

### 1. Separate shared model from server-only registry

Refactor Policy Intelligence so:

- shared types, enums, public projection types, labels and pure validation helpers live in a client-safe module;
- the actual editorial registry/content source lives in a module guarded by:

```ts
import "server-only";
```

Do not rely only on naming conventions.

The module boundary should make accidental client import of the editorial registry fail during build/development.

### 2. Repository-backed manual content

Create a simple repository-owned location for manually curated policy entries.

Use the smallest maintainable approach consistent with Next.js and the repository.

A typed TS registry or statically imported validated content files are acceptable.

Do NOT use runtime writes to local files.

Do NOT create a CMS.

Do NOT create a database table.

Requirements:

- Git diff clearly shows editorial changes;
- entries preserve the existing PolicyEntry semantics;
- review/publish status remains explicit;
- adding a future draft must not make it public;
- no fake production policy data is required in this task.

If you introduce a template/example, it must not be loaded as production content.

### 3. Public projection

Create an explicit public-safe projection.

Conceptually it should include only fields needed by public pages.

Do not pass internal/discovery/review-only fields to client presentation.

At minimum preserve public behavior for:

- id/slug;
- source/legal status;
- published editorial state if still needed publicly;
- public source identity;
- localized public copy;
- public lawyer commentary only when explicitly published in the record.

If there are future internal notes or discovery metadata, keep them server-only.

Do not overengineer the projection.

### 4. Server-load public routes

Change the public route boundary so the server loads published policy data and passes only public-safe data into client components.

Required surfaces:

- Home policy preview;
- `/intelligence` list;
- `/intelligence/[id]` detail.

The existing client UI may remain client-rendered for search/filter/locale interaction, but it must receive published data as props rather than importing the editorial registry.

The detail route must resolve the slug on the server.

Unknown/unpublished slugs must continue to use `notFound()`.

### 5. Home integration

The root route is currently a server component that renders a client `ImmigrationServiceHome`.

Use that server boundary if appropriate.

Home must receive only published policy preview data.

Do not import unpublished registry data from the client Home component.

### 6. List/search integration

Client-side search/filtering is allowed over the already-published projection passed from the server.

It must not call a route that exposes draft/review content.

No public API for unpublished records.

### 7. Manual curation workflow documentation

Add concise repository documentation for adding/updating a policy manually.

Prefer a small document near the content source, for example:

`chatbot/content/policy-intelligence/README.md`

or another location consistent with the chosen implementation.

Document this interim workflow:

```text
1. verify official source
2. add/update repository editorial entry
3. start as draft or review_required
4. validate locally
5. lawyer/project-owner review
6. change editorial status to published only after approval
7. inspect Git diff
8. commit/release through normal project workflow
```

State clearly:

- changing source/legal status is different from publication status;
- proposals remain proposals even when published editorially;
- official excerpt must be verbatim source data;
- no automatic publication;
- no fake lawyer commentary;
- no runtime file editing in production.

### 8. Validation command

If useful, add a lightweight validation script or package command that validates the repository editorial registry.

Reuse existing TypeScript/tsx tooling.

Do not add a new framework.

A command conceptually like:

```text
pnpm policy:validate
```

is acceptable if it provides real value.

Do not make validation depend on network access.
