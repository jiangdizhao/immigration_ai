## Goal

Replace appointment placeholders with a durable, secure, Chinese-first bilingual consultation workflow that can actually move a customer from a request for a meeting to a staff-proposed slot and an explicitly confirmed consultation.

P11-008 is a scheduling/service workflow. It is not a legal-reasoning feature, not a calendar-provider integration, not a payment/pricing feature, and not a matter-wide staff browser.

## Actors

### Customer

Must be:

- authenticated;
- non-guest;
- email verified;
- role `user`.

Customer may:

- create consultation request;
- list/read own requests;
- confirm a staff proposal;
- request rescheduling;
- cancel a non-terminal request.

### Admin

May:

- list/read all consultation requests;
- assign/unassign a verified lawyer;
- propose/re-propose a slot;
- cancel;
- mark a confirmed consultation completed.

### Lawyer

May:

- list/read only consultations assigned to their user ID;
- propose/re-propose a slot for an assigned request;
- cancel an assigned request;
- mark an assigned confirmed consultation completed.

A lawyer must not self-assign arbitrary consultation requests.

## Continuity / least privilege

A consultation may optionally link to:

- an owned `Chat` / `ImmigrationConversation`;
- an owned `LawyerClarificationRequest`.

The server must validate ownership before persisting either link.

If a chat is linked, derive `legalMatterId` from the owned server record; never trust a client-supplied matter ID.

These links do not widen staff authorization:

- appointment assignment does not grant full chat history;
- appointment assignment does not grant MatterDocument access;
- appointment assignment does not grant unrelated lawyer-request access;
- appointment assignment does not grant arbitrary Legal Service Matter access.

Normal staff appointment projections should contain only scheduling-safe data: customer identity, customer note, preferred windows/timezone/method, appointment state, assigned lawyer identity, and staff-proposed slot/method/instructions.

## Proposed schema

Use additive schema. Exact naming may follow repository conventions, but preserve the contract below.

### ConsultationRequest

Required concepts:

- `id` UUID primary key;
- `userId` owner, FK -> User, RESTRICT;
- optional `chatId`, FK -> Chat, SET NULL;
- optional server-derived `legalMatterId`;
- optional `lawyerClarificationRequestId`, FK -> LawyerClarificationRequest, SET NULL;
- `status`: `requested | proposed | confirmed | completed | cancelled`;
- `customerTimezone`: bounded IANA timezone string;
- `preferredWindows`: JSON array, max 3 validated future windows stored as normalized UTC instants;
- `methodPreference`: `video | phone | in_person | no_preference`;
- bounded `customerNote`;
- optional `assignedLawyerUserId`, FK -> User, SET NULL;
- optional `assignedAt`;
- optional scheduled `startAt` / `endAt`;
- optional `scheduledMethod`: `video | phone | in_person | other`;
- optional bounded `meetingInstructions`;
- optional `proposedAt`, `confirmedAt`, `completedAt`, `cancelledAt`;
- `createdAt`, `updatedAt`.

Indexes should support:

- customer history by owner/status/update time;
- admin queue by status/update time;
- assigned-lawyer queue by lawyer/status/update time;
- overlap query by lawyer + scheduled interval/status.

### ConsultationEvent

Immutable audit/event rows:

- `id`;
- `consultationRequestId`;
- optional actor user ID;
- actor role `customer | lawyer | admin | system`;
- bounded event type;
- optional from/to status;
- bounded metadata containing scheduling transition facts only;
- created timestamp.

Do not store secrets, auth tokens, raw chat content, document text, or provider payloads in event metadata.

## Time contract

All server persistence is UTC-consistent with the existing chatbot DB session policy.

Customer timezone must be a valid IANA timezone accepted by the server runtime.

Preferred windows:

- maximum 3;
- each has `startAt < endAt`;
- each must be in the future when submitted;
- reject malformed/duplicate/overlapping windows from the same request;
- use bounded horizon/length validation chosen conservatively and documented in tests.

Staff proposal:

- requires assigned lawyer;
- requires valid concrete `startAt < endAt`;
- requires a scheduled method;
- meeting instructions are optional bounded plain text;
- proposed/confirmed appointments for the same lawyer must not overlap.

## Concurrency / overlap invariant

Do not rely only on client checks.

When proposing/re-proposing a slot:

1. acquire a transaction-scoped per-lawyer advisory lock or an equivalently strong repository-compatible serialization mechanism;
2. re-read the current request/state;
3. query other `proposed` or `confirmed` consultations for that lawyer whose half-open interval overlaps `[startAt, endAt)`;
4. reject with a domain conflict if overlap exists;
5. update state and append the immutable event in the same transaction.

This protects against two concurrent staff actions booking the same lawyer into overlapping slots.

## State machine

Baseline:

```text
requested -> proposed -> confirmed -> completed
```

Allowed side paths:

- requested -> cancelled;
- proposed -> requested when customer requests rescheduling;
- proposed -> proposed when authorized staff re-proposes;
- proposed -> cancelled;
- confirmed -> proposed when authorized staff must replace the slot; fresh customer confirmation is required;
- confirmed -> cancelled;
- confirmed -> completed;
- completed and cancelled are terminal.

Invalid transitions must fail server-side.

Customer confirmation must use optimistic/current-state validation so a stale proposal cannot be confirmed after it has been replaced.

### Stage 1 API rules

Customer create must not accept:

- `assignedLawyerUserId`;
- `legalMatterId`;
- staff slot fields;
- staff meeting instructions.

If `chatId` or `lawyerClarificationRequestId` is supplied, re-authorize ownership and derive safe linkage server-side.

Lawyer routes must enforce `assignedLawyerUserId === session.user.id`.

Return allowlisted DTOs; do not spread raw DB rows when that would expose fields not intended for the actor.

### Stage 1 tests

At minimum:

#### Customer access

- unauthenticated rejected;
- guest rejected;
- lawyer/admin cannot use customer-create route as ordinary customer;
- customer can create/list/read own request;
- customer cannot read another customer's request;
- linked chat ownership is enforced;
- linked lawyer request ownership is enforced;
- client-supplied matter/assignment escalation is impossible.

#### Validation

- invalid timezone rejected;
- zero windows rejected if windows are required by chosen contract;
- >3 windows rejected;
- malformed/reversed/past windows rejected;
- duplicate/overlapping customer windows rejected;
- oversized note/instructions rejected;
- invalid method rejected.

#### Assignment / staff RBAC

- admin can assign verified lawyer;
- admin cannot assign user/unverified/guest;
- lawyer sees only assigned consultations;
- another lawyer receives 403/no disclosure;
- lawyer cannot self-assign.

#### State machine

- requested -> proposed;
- proposed -> confirmed;
- proposed -> requested reschedule;
- confirmed -> proposed re-proposal;
- confirmed -> completed;
- cancellation from allowed states;
- terminal-state mutation rejected;
- stale confirmation rejected after re-proposal.

#### Overlap

- same lawyer overlapping proposed/confirmed slot rejected;
- adjacent half-open intervals allowed;
- different lawyers may have overlapping clock times;
- cancelled/completed historical requests do not block a new slot;
- concurrency/serialization behavior is covered at the service boundary as far as the repository test environment permits.

#### Audit

- creation, assignment, proposal, confirmation, reschedule, cancellation and completion write immutable events;
- failed transaction does not leave partial state/event mutations.

### Time-input implementation

Initial Stage 2 UI uses the browser/system timezone only:

1. obtain `Intl.DateTimeFormat().resolvedOptions().timeZone`;
2. validate that a non-empty IANA timezone was resolved;
3. display the timezone near the preferred-window controls;
4. use native `datetime-local` inputs;
5. convert each local value with `new Date(value).toISOString()`, which is valid only because the stored customer timezone is the same browser/system timezone;
6. do not allow an arbitrary different timezone label without a correct timezone-aware conversion implementation.

Display stored preferred/proposed times with `Intl.DateTimeFormat(..., { timeZone: consultation.customerTimezone })`.

### History/detail behavior

History must show safe customer fields only:

- status;
- updated/created time;
- preferred windows;
- assigned yes/no;
- proposed/confirmed slot when present.

Detail must show:

- preferred windows and timezone;
- method preference;
- optional customer note;
- staff proposal, scheduled method and meeting instructions when present;
- lifecycle/status information;
- no lawyer login identity.

Customer actions:

- `requested`: cancel;
- `proposed`: confirm / request reschedule / cancel;
- `confirmed`: cancel;
- `completed|cancelled`: no mutation controls.

All mutations send the current `expectedRevision`. On 409 stale conflict, reload the consultation and show a localized “updated elsewhere / please review” message instead of retrying automatically.
