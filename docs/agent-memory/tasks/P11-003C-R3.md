## Finding 1 — real Home Affairs alert URLs are commonly relative

The real `siteData.alertItems` payload contains values such as:

`/Visa-subsite/Pages/work/186-employer-nomination-scheme.aspx`

The current R2 code passes raw alert URL strings directly into `assertOfficialUrlAllowed()`. That helper expects an absolute URL, so valid root-relative Home Affairs paths are rejected and candidates fall back to the configured seed URL.

Correct behavior:

1. Take each raw alert URL in source order.
2. Resolve it against the already fetched and allowlisted `page.finalUrl`, e.g. with `new URL(rawUrl, page.finalUrl)`.
3. Pass the resolved absolute URL through the existing canonicalisation + HTTPS + exact-host allowlist validation.
4. Accept the first safe usable alert URL.
5. Reject/ignore out-of-scope absolute or resolved URLs.
6. Do NOT fetch the alert URL.
7. Use seed fallback only when no safe usable alert URL exists.

Do not invent URLs.

## Finding 2 — generic fetched-page provenance is mislabeled

The R2 candidate metadata currently uses a provenance-kind field whose value is `"seed"` for generic `candidateFromPage()` records, including child/detail pages discovered from a listing or sitemap.

That is semantically inaccurate.

Refine the provenance-kind contract so it truthfully distinguishes, at minimum:

- a Home Affairs alert URL;
- an explicit seed fallback;
- a fetched page/detail URL.

Naming is your technical choice. Prefer a clear field name such as `urlProvenance` rather than a field named like it contains a URL when it actually contains a kind.

Keep this provenance-only. Do not add legal meaning.
