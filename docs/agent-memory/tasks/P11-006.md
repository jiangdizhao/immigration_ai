# P11-006 — Matter-centered Client Portal

**Status:** VERIFIED

## Goal

Create a Chinese-first, bilingual registered-customer portal that makes the existing production system feel matter-centered without redesigning its database.

The portal should let a customer answer:

- What matters/conversations do I currently have?
- What facts are already confirmed and what still needs confirmation?
- What customer documents belong to this matter and what is their processing state?
- Is a lawyer review pending, updated, waiting for me, or closed?
- What is my VIP/Premium entitlement state?
- Where do I continue: AI Workspace, lawyer-review detail, document work, or membership management?

The portal is an aggregation/continuity layer. It is not a new legal reasoning engine, document store, lawyer workflow or booking system.

### Legal-service Matter

The chatbot may server-fetch legal-service `GET /matters/{matter_id}` only after ownership of that exact matter ID has been established through the authenticated customer's owned `ImmigrationConversation` records.

Do not expose `MatterOut.metadata_json` directly to the browser.

## Portal identity model

Use deterministic grouping without a migration:

```text
if conversation.legalMatterId is non-null:
    portalGroupKey = "matter:" + exact legalMatterId
else:
    portalGroupKey = "chat:" + chatId
```

Rules:

- conversations with the same exact non-null legalMatterId may be grouped as one portal matter;
- a chat-backed group without legalMatterId must be labelled as a conversation / provisional matter context, not a fully established legal matter;
- do not merge by title, visa type, email, semantic similarity or model inference;
- the most recently updated owned conversation in a group is the default continuation chat.

## Authentication / role boundary

`/client-portal` is for registered customer accounts.

- unauthenticated/guest -> login/registration path;
- customer role -> portal;
- lawyer -> existing `/lawyer-portal`;
- admin -> existing `/admin-portal`.

Do not make the customer portal a generic staff data browser.

## Server-side portal projection

Prefer one bounded server/API projection, e.g. `/api/client-portal`, backed by a dedicated server service/helper.

The browser should not independently stitch arbitrary matter IDs together.

Project a bounded view model, conceptually:

```text
ClientPortalView
  account
  summaryCounts
  matterGroups[]
  recentActivity[]
```

Each `matterGroup` may contain:

- group key;
- `legalMatterId | null`;
- provisional flag;
- display title from owned conversation data;
- owned chat summaries;
- default/most-recent chat ID;
- last activity timestamp;
- safe matter snapshot;
- safe document summaries/counts;
- safe lawyer-request summaries/counts;
- next-action links.

No storage key, SHA, extracted evidence text, raw message history or provider identifiers.

## Legal-service Matter projection

When a real linked `legalMatterId` exists, server-side fetch the existing legal-service Matter record with a bounded timeout and fail-soft behavior.

Project only customer-safe fields such as:

- matter ID;
- matter status as returned by the backend, clearly labelled as system/matter state rather than a legal outcome;
- issue summary;
- issue type;
- visa type;
- risk level if present;
- bounded confirmed facts from `metadata_json.compact_state_v2.confirmed_facts`;
- bounded unresolved/to-confirm items from legacy `fact_slot_states` whose statuses are missing, user_unsure, document_unavailable or conflicting;
- interaction progress / next action only when already represented in structured backend state.

Do not expose:

- raw `metadata_json`;
- chain-of-thought/internal reasoning;
- retrieval debug;
- model prompts;
- research ledger contents;
- raw conversation_history;
- provider/model telemetry.

### Fact provenance

Portal facts must preserve status semantics.

A safe presentation split:

```text
Confirmed by you / 已确认信息
    <- compact_state_v2.confirmed_facts

To confirm / 待确认
    <- missing/user_unsure/document_unavailable/conflicting structured fact slots
```

Do not render `llm_extraction` or `system_inferred` values as confirmed customer facts.

## MatterDocument projection

Aggregate only documents belonging to the authenticated customer's owned chats in the group.

Portal document summary may expose:

- document ID;
- chat ID;
- filename;
- MIME/display format;
- byte size;
- processing status;
- security status;
- created/updated timestamps;
- latest terminal extraction run status/method/truncated flag if cheaply available.

Never expose:

- storageKey;
- SHA-256;
- extracted text;
- evidence units;
- private object URLs.

`securityStatus=pending` must not be labelled safe/clean/verified.

The portal may deep-link back to the corresponding AI Workspace chat for full document actions.

## Lawyer-request projection

Use existing customer-owned lawyer-request summaries.

Expose only safe fields already available to the customer:

- request ID;
- chat ID / legal matter ID;
- status;
- assigned boolean;
- unread/update available;
- created/updated/reviewed timestamps;
- short bounded question preview if needed.

Do not duplicate lawyer message threads or evidence snapshots into the portal overview.

Deep-link to the existing authorized detail page.

Operational priority may be derived only from explicit request state:

1. `needs_more_information` / unread update;
2. pending or in_review;
3. confirmed/corrected;
4. closed.

Do not infer lawyer availability or response SLA.

## VIP / account projection

Reuse existing entitlement/billing logic.

Show:

- free/VIP;
- active/expired;
- expiry/current-period end if already exposed by existing safe API;
- cancel-at-period-end state;
- Premium availability.

Do not expose provider customer IDs, subscription IDs, payment method data or webhook metadata.

The portal links to existing `/vip` management.

## Matter card / selected matter sections

Recommended selected matter sections:

1. Matter overview
   - title
   - linked legal matter ID when real
   - issue/visa type if authoritative
   - last activity

2. Confirmed facts
   - bounded user-origin facts only

3. To confirm
   - structured missing/uncertain/conflicting fields only

4. Documents
   - count + recent safe metadata/status
   - CTA to continue in AI Workspace for document actions

5. Lawyer review
   - status/unread/needs-information summaries
   - links to existing request detail

6. Conversations
   - all owned chats in this exact matter group
   - most recent first
   - continue/open AI Workspace

7. Membership
   - compact account entitlement card
   - `/vip` CTA

## Recent activity

A bounded activity stream may be derived from owned records only:

- conversation updated;
- document uploaded/updated;
- lawyer request created/updated.

Keep at most ~20 recent items.

Do not manufacture legal milestones from message text.

## Existing pages / navigation

P11-006 may add bilingual back-links / shared portal framing to existing customer lawyer-request and VIP pages, but must not rewrite their backend workflows.

## API / performance boundaries

- no unbounded N+1 across hundreds of chats;
- cap portal conversations/groups (e.g. 50–80 consistent with current product bounds);
- batch/query document and lawyer-request summaries by authenticated owner where practical;
- unique legalMatterId server fetches only, bounded concurrency;
- legal-service matter fetch must have an explicit short timeout and fail soft per matter;
- one unavailable matter snapshot must not break the entire portal;
- do not fetch raw document evidence for the portal.
