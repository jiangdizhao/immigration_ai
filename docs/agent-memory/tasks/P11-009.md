## 5. Required implementation

### 5.1 Rollout-safe schema availability

Add a small server-only availability boundary, following the proven consultation `to_regclass` pattern where appropriate.

Required semantics:

- exact catalog detection for the Stage-1 Policy Intelligence schema;
- when schema is available, DB-backed published data is canonical;
- available schema + zero current published records = a genuine empty live feed;
- unavailable schema != zero published records;
- if schema is unavailable, existing published `MANUAL_POLICY_ENTRIES` may be used as compatibility/editorial fallback;
- if schema is unavailable and manual fallback is empty, render an explicit bilingual unavailable/not-yet-activated state rather than an authoritative zero-content claim;
- unexpected/unrelated DB errors must not be broadly swallowed or silently converted to manual data.

Do not apply migration 0023.

### 5.2 Public-safe Stage-2 DTOs

Create explicit public product DTOs rather than passing raw Stage-1 DB rows or analysis payloads directly into client components.

For automated current published records, public data may include only what is needed for presentation, such as:

- item ID + stable slug;
- source status;
- authority + official title + official HTTPS URL;
- source/effective dates when actually present;
- current revision number + generated/published timestamps;
- bilingual title + executive summary;
- key changes;
- affected groups;
- practical impacts;
- recommended actions;
- transition information;
- uncertainties/applicability limits;
- bounded importance dimensions;
- a human-readable public source-family/category label;
- whether the analysis is AI-generated.

Do NOT expose:

- `normalizedEvidence` or raw snapshot text;
- verification assessments/reason codes;
- material-claim internals unless a separately justified public projection is designed;
- model/provider metadata;
- analysis fingerprint;
- sourceConfigId/sourceId/internal telemetry;
- sync errors/failure counts;
- draft/review-required/held revisions;
- raw backend IDs that the UI does not need.

Do not manufacture `officialExcerpt` from AI analysis or from arbitrary normalized source text.

### 5.3 Provenance presentation

Every automated record must visibly distinguish:

1. **Official source** — authority, official title, status/date metadata and link;
2. **AI-generated interpretation** — clearly labelled as AI-generated analysis, not official law and not lawyer advice;
3. **Lawyer commentary** — show only if actual lawyer-authored/reviewed content exists.

If lawyer commentary does not exist, show a neutral localized absence state. Never copy a mock lawyer identity/comment from `UI_template`.

Use a repository-consistent dynamic/no-store boundary so successful future policy syncs are not frozen into a build artifact.

Preserve Chinese-first locale behavior and English switching.
