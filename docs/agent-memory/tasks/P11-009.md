## 5. Required implementation

### 5.1 Durable persistence and migration artifact

Inspect existing Drizzle conventions before designing names. Add the smallest coherent schema capable of representing at least:

- stable Policy Intelligence item identity;
- official-source snapshots;
- AI analysis revisions;
- sync-run/attempt observability.

The model may choose repository-consistent names, but the semantics must cover the following.

#### Stable policy item

Must preserve:

- stable internal ID;
- stable slug/public identity;
- primary source family/source ID;
- canonical official URL identity;
- current lifecycle/publication pointers;
- timestamps.

Do not use title text as the sole identity.

#### Official-source snapshot

Each snapshot must be immutable and retain enough backend-held evidence to audit an analysis revision:

- policy item / source linkage;
- canonical official URL;
- configured authority/source ID;
- official/discovered title;
- retrieval timestamp;
- HTTP/content metadata needed for provenance;
- normalized bounded source text or equivalent auditable backend-held evidence representation;
- cryptographic content hash;
- explicit source date/effective date only when established by the source semantics;
- previous/current relationship or deterministic ordering.

A changed source hash creates a new snapshot. An unchanged source must not silently create duplicate analysis revisions on every sync.

Do not overwrite historical snapshots.

#### Analysis revision

Persist a structured bilingual revision linked to the exact snapshot/evidence set that produced it. At minimum the schema/typed payload must support:

- zh-CN and English executive summary;
- key changes;
- affected groups;
- practical impacts;
- recommended user actions / next checks;
- transition/grandfathering information when evidenced;
- uncertainties / applicability limits;
- related official sources actually snapshotted;
- importance signals used for later deterministic sorting;
- material claims with evidence references;
- model/config metadata sufficient for audit without storing chain-of-thought;
- verification result;
- publication lifecycle/state;
- generated/published/superseded timestamps.

Do not persist hidden chain-of-thought.

#### Sync run

Persist bounded operational metadata such as:

- source/config ID;
- start/end/status;
- discovered/snapshotted/unchanged/analyzed/published/held/failure counts;
- safe error code/classification;
- no secrets, prompts, raw credentials or customer data.

#### Migration rule

Generate the next additive migration using the repository's existing Drizzle workflow. Current history already contains 0018–0022; verify the journal before generation and never rewrite those pushed migrations. The expected next migration may be 0023 if the repository state still warrants it.

**MIGRATION MUST NOT BE APPLIED** to the normal local database, retained P11-008 disposable database, staging or production in this task.

### 5.2 Safe official-source acquisition

Reuse the P11-003C discovery and network-security foundation rather than creating a second arbitrary crawler.

Stage 1 must add the ability to fetch the actual authoritative candidate/detail source needed for analysis, while preserving or strengthening:

- HTTPS only;
- configured host allowlist;
- redirect revalidation;
- DNS rejection of private/local/link-local/special destinations;
- no credential/cookie forwarding;
- content-type constraints;
- bounded decoded bytes;
- one full-operation deadline spanning DNS/redirect/headers/body;
- no arbitrary URL CLI mode;
- canonical URL normalization;
- deterministic source/hash deduplication.

Home Affairs alert pointers may now be followed only through this new bounded authoritative-acquisition path after the existing validation boundary. Do not weaken the earlier rule merely to obtain content.

If a candidate cannot be safely/meaningfully acquired, hold/skip it; do not invent source text.

### 5.3 Backend-controlled evidence packet

The AI analyzer must receive only backend-controlled official-source evidence.

Related sources may be used only if they are:

1. derived through the configured/allowlisted official-source logic;
2. actually fetched through the safe acquisition boundary; and
3. represented as source snapshots/evidence refs before analysis.

Do not let provider-native/open-ended web search become publication authority.

Keep evidence bounded and deterministic enough for reproducible tests.

### 5.4 Structured bilingual AI analyzer

Add a dedicated Policy Intelligence analyzer service/adapter rather than reusing customer-answer prompts.

Preferred production model policy:

- GPT-5.6 Sol;
- high reasoning;
- operator-configurable model/effort through environment/config rather than scattering literals;
- no retries/continuations that create unbounded behavior;
- bounded timeout and output contract.

Follow existing provider abstraction patterns in the repository where appropriate.

The analyzer output must be a strict versioned structured contract. It must not write prose directly into the public UI.

Requirements:

- output both zh-CN and English;
- preserve official source identity separately from interpretation;
- never fabricate lawyer commentary;
- never place AI text in `officialExcerpt`;
- distinguish explicit source facts from inferred practical interpretation;
- treat uncertain effective/commencement dates and legal status as uncertainty, not confident facts;
- include claim-level evidence references for material legal/policy claims;
- include applicability/uncertainty fields rather than forcing certainty.

No live paid-provider call is required for Stage-1 implementation validation. Use deterministic injected/fake provider responses in tests.

### 5.5 Independent Policy Analysis Verifier

Implement a dedicated evidence-bound verifier for Policy Intelligence. Do not wire the customer Phase-6 checker directly into this pipeline, but reuse its architectural lessons:

- verifier receives the structured analysis plus bounded backend-held source evidence;
- no research/tools from the verifier;
- no arbitrary web;
- claim-level support result;
- evidence refs must resolve to the exact source snapshot/evidence packet;
- malformed/unknown refs fail validation;
- unsupported decisive claims cannot pass publication.

Use a small structured verdict vocabulary, for example `supported | partial | unsupported`, plus overall publication eligibility. Exact names may follow repository conventions.

Verifier failure must be fail-closed.

### 5.6 Deterministic auto-publication gate

Automatic publication is authorized only when all required gates pass.

At minimum hold/review rather than publish when:

- source acquisition is incomplete or unsafe;
- canonical source identity is missing;
- legal/source status is unresolved in a material way;
- effective/commencement semantics are asserted but unsupported;
- decisive claims are unsupported;
- evidence refs are missing/invalid;
- bilingual required content is incomplete;
- analyzer/verifier contract is malformed;
- provider/verifier fails or times out.

Supported claims may be published. Partial/conditional material should be represented explicitly as uncertainty/limits, not silently upgraded to certainty.

Unsupported material must not appear in a published revision.

The publication transition must be deterministic and auditable. Publishing a new verified revision must supersede the previous published revision without deleting history.

### 5.7 Importance signals

Stage 1 should persist structured importance signals for Stage 2 sorting. Do not expose or market a pseudo-scientific 0–100 AI confidence score.

Use bounded interpretable dimensions such as:

- breadth of affected users;
- legal force/status;
- immediacy;
- immigration/study-service relevance;
- material procedural/compliance impact.

If a numeric aggregate is used internally, compute it deterministically from validated bounded dimensions and keep the dimensions auditable.

### 5.8 Server-side read service

Add server-only read functions capable of returning:

- latest published policy list/projections;
- one published policy by slug;
- revision/history metadata needed by Stage 2;
- latest successful sync timestamp/status.

Do not yet replace the public UI with the new source unless doing so is necessary for a focused compile/test seam. Stage 2 owns visible activation.

The existing manual registry may remain as compatibility/editorial fallback. Do not delete it in Stage 1 unless a direct compile/architecture requirement proves necessary.

### 5.9 Operator sync command

Add one bounded operator command, preferably consistent with the existing `pnpm policy:discover` tooling, for example:

```bash
pnpm policy:sync -- --source home-affairs-guidance
```

Exact syntax may follow repository conventions.

It must support deterministic fixture/test operation without paid provider or live network access.

A normal sync should conceptually:

```text
discover
 -> acquire changed official source
 -> snapshot
 -> analyze when needed
 -> verify
 -> publish or hold
 -> persist safe run telemetry
```

Idempotence matters: unchanged source content should not generate an unlimited stream of equivalent snapshots/revisions.

Do not add EventBridge, cron or AWS scheduling in Stage 1. Stage 4 owns production scheduling.
