## 3. Mandatory Stage-3 source work

### S3-1 — Production chatbot image and native-runtime verification

Inspect the current `chatbot/Dockerfile.local`, parser-worker tracing, package/lock state and production scripts.

Create a production-oriented chatbot image/runtime path suitable for later ECS/Fargate use.

Requirements:

- normal app startup must NOT automatically run DB migrations;
- build, migrate and start responsibilities must be separate;
- preserve `outputFileTracingIncludes` for document parser worker assets;
- include all runtime dependencies required by document parsing;
- add a small deterministic native-runtime verification command/script that:
  - loads `@napi-rs/canvas`;
  - performs a minimal in-memory canvas operation;
  - loads/locates the document parser worker runtime artifact;
  - exits non-zero on missing/incompatible native binding;
  - prints package/runtime architecture/version evidence but no secrets;
- do not hardcode an ECS CPU architecture that has not yet been inspected;
- make the verification reusable in Stage 4 against the actual image/task architecture.

A local Docker build/self-test may be run only if it requires no protected resource and no external production service. Failure to build because the local environment lacks Docker must be reported, not worked around by weakening the check.

### S3-2 — Migration/start separation and migration safety preflight

Current production-like helpers must no longer imply that normal service start migrates shared databases.

Provide explicit commands/scripts for:

- build;
- service start;
- one-off migration execution;
- migration target preflight.

The migration preflight must:

- display only safe target identity (database name/server/ledger latest entry);
- reject clearly protected/forbidden target names when invoked in a test-only mode;
- require an explicit operator acknowledgement/flag before any migration execution wrapper proceeds;
- never print credentials/full URLs;
- use the repository migration chain through the current head;
- not guess that 0018–0021 alone is current.

This coding task must NOT connect to a database and must NOT apply migration 0023 or any other migration.

If a schema change appears necessary, STOP. Do not create 0024 automatically.

### S3-3 — MatterDocument stale-storage recovery

Implement bounded operator-only maintenance for stale object-storage intents.

Cover at least:

- stale `uploading`;
- stale `cleanup_pending`;
- recoverable `storage_failed` where cleanup retry is meaningful.

Requirements:

- dry-run by default;
- explicit age cutoff;
- bounded batch size;
- deterministic ordering;
- compare-and-set/state-aware operations;
- idempotent S3 delete semantics;
- no customer-facing endpoint;
- no filenames/document text/storage keys in normal summary logs;
- safe counts/IDs only;
- one failure must not silently corrupt unrelated records.

Reuse existing storage cleanup semantics where possible instead of inventing a second lifecycle.

### S3-4 — Retention/purge operation

Implement an explicit operator-only retention/purge path for soft-deleted MatterDocuments.

Requirements:

- no implicit/default legal retention period;
- operator must provide an explicit cutoff or policy input;
- dry-run by default;
- bounded batch;
- delete private object first;
- only after successful/idempotent object deletion may DB metadata/processing/evidence be hard-purged;
- DB/S3 failure must leave a recoverable record rather than an orphaned object;
- active/non-deleted documents must never be selected;
- currently-processing records must fail closed or be excluded deterministically;
- no customer document body/filename/storage key in ordinary logs.

Prefer no schema change. If durable new lifecycle state is genuinely required, STOP and report before generating a migration.

### S3-5 — Malware/quarantine fail-closed boundary

P11-005 already has `securityStatus = pending|clean|rejected|failed`, but production readiness requires actual enforcement.

Implement these invariants:

- upload remains `pending`; never mark a document clean merely because format validation/parsing succeeds;
- document processing requires `securityStatus === "clean"`;
- document selection/evidence construction for AI requires clean;
- lawyer-request document reconstruction/handoff requires clean;
- rejected/failed/pending documents fail closed with customer-safe/operationally safe behavior;
- no raw scanner output leaks to customers.

Add a provider-neutral scanner/reconciliation service boundary and deterministic fake/test adapter.

The source task does NOT need to choose/configure a real AWS malware product. Document the Stage-4 integration contract needed to turn an external scanner verdict into the existing security state.

Do not invent a production scanner verdict.

### S3-6 — Private S3 security preflight

Add an injectable production-preflight boundary/CLI for later Stage-4 use.

- configured bucket exists in the expected region;
- server-side encryption posture is acceptable;
- S3 Block Public Access protections are enabled;
- bucket policy is not public;
- app never depends on public object URLs.

Use injected AWS clients in tests.

The Stage-3 coding task must NOT contact AWS.

Effective role write/read/delete smoke and real bucket/IAM verification are Stage-4 environment evidence.
