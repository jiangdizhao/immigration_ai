# P11-007 — Lawyer Workspace Continuity

**Status:** ACTIVE — READY TO IMPLEMENT  
**Milestone:** Phase 11  
**Planning checkpoint:** `596ea345ee9df673f183aa1f8230034201fe36d4`  
**Task granularity:** one major task packet; routine corrections remain inside P11-007.

## Goal

Rebase the existing assigned-lawyer portal into a Chinese-first bilingual human-review workspace that preserves the customer's handoff context without expanding lawyer authority.

The lawyer should be able to answer:

- Which assigned requests need my action?
- What did the customer actually ask?
- What AI answer am I reviewing?
- What bounded conversational context was handed off?
- Which official/legal sources supported the AI answer?
- Which customer-provided document excerpts were supplied to the AI?
- Has the customer added a clarification/reply?
- Should I confirm, correct, request more information, or close the request?
- If I correct or confirm it, what optional feedback should enter the existing learning bridge?

P11-007 is a human-service continuity/presentation task. It is not a new case-management database or a new legal reasoning system.

## Queue design

The lawyer queue remains assigned-only and bounded to the existing 100-request limit unless a smaller UI projection is chosen.

Use explicit request state, not AI inference, to organize work.

Recommended operational categories:

### Needs lawyer action

- `pending`
- `in_review`

### Waiting for customer

- `needs_more_information`

### Reviewed

- `confirmed`
- `corrected`

### Closed

- `closed`

Do not invent urgency, deadlines, SLA timers or unread state for lawyers. There is currently no lawyer-last-viewed authority.

Queue cards may show:

- request ID only in secondary/detail form;
- customer email;
- exact status;
- assistant mode;
- linked legal matter ID when present;
- bounded question preview;
- created/updated/assigned timestamps.

Do not expose internal user IDs, reviewer IDs or learning/debug identifiers in the primary queue.

## Detail workspace information architecture

Recommended order:

1. **Request header**
   - customer email
   - request status
   - assistant mode
   - linked matter ID if present
   - created/updated/reviewed timestamps

2. **Customer question**
   - immutable `questionSnapshot`

3. **AI answer under review**
   - immutable `answerSnapshot`
   - visually labelled AI analysis, not lawyer advice

4. **Customer note**
   - if present

5. **Handoff context**
   - typed rendering of the bounded `contextSnapshot`
   - retain role + text + ordering
   - label clearly as the captured handoff context, not the full live conversation

6. **Official / legal evidence**
   - `citation` and `compact_source` items
   - title / authority / used-for / bounded quote / URL where present
   - clearly styled as source material, not customer evidence

7. **Customer document evidence**
   - only `customer_document` snapshot items
   - filename
   - run/extraction status
   - formatted locator
   - bounded exact quote
   - truncation warning
   - no storage key
   - no raw object URL
   - no arbitrary document download

8. **Clarification thread**
   - existing request messages
   - explicit role labels
   - chronological timestamps

9. **Lawyer disposition workspace**
   - lawyer response
   - corrected answer
   - valid status actions
   - optional advanced learning-feedback controls

## Snapshot bounds

The immutable snapshot is already bounded by creation rules.

The lawyer projection should nevertheless enforce defensive UI/API bounds.

Recommended:

- context items: max 8
- context text per item: max 8,000 chars, but prefer existing stored text without expansion
- legal evidence items: max 40
- customer-document evidence items: max 24
- evidence quote display/API projection: respect stored bounded snapshot; do not reconstruct from MatterDocument tables in P11-007
- messages: existing request-thread rows; cap projection to a defensible bound such as 100 if needed

Do not fetch additional context to "complete" the snapshot.

## Status/action semantics

Preserve the current state machine exactly:

- pending -> in_review / confirmed / corrected / needs_more_information / closed
- in_review -> confirmed / corrected / needs_more_information / closed
- needs_more_information -> in_review / closed
- confirmed -> closed
- corrected -> closed
- closed -> terminal

Server validation remains authoritative.

UI should show/enable only actions valid for the current status where practical.

Substantive response requirements remain:

- `needs_more_information` requires lawyer response;
- `confirmed` requires lawyer response;
- `corrected` requires lawyer response + corrected answer.

Do not weaken these rules.

## Clarification thread

Preserve the existing customer reply rule:

- customer may reply only when request is `needs_more_information`;
- customer reply moves request back to `in_review`.

The lawyer UI should make the thread easy to scan but does not introduce a free-form real-time chat state machine.

P11-008, not P11-007, owns real appointment/live consultation workflow.
