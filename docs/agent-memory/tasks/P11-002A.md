## Scope

### 1. Reusable public-content model

Create one small typed content source for the four public pages rather than scattering bilingual text across components.

It should:

- support `zh-CN` and `en`;
- integrate with the existing P11-001 locale foundation;
- keep public-page copy separate from backend answer-language behavior;
- keep service definitions reusable between Home and Services;
- keep lawyer mock profiles replaceable from one place;
- make later P11-002B visual changes possible without rewriting content logic.

Use repository conventions for naming/location. Do not introduce a heavy i18n framework.

### 2. Home page

Reframe Home as an Australian immigration + study service platform.

The first screen should make clear:

- what the platform helps with;
- that AI can be used for first-contact/intake;
- that human lawyer service is available when appropriate.

Home should include, at minimum:

- service-platform hero;
- clear AI consultation CTA;
- human-lawyer/consultation CTA;
- overview of the six service families;
- a simple “how it works” flow;
- a lawyer/team preview section using explicit placeholder profiles;
- restrained trust/provenance language consistent with the content policy.

Do not add invented statistics, success rates, lawyer credentials or office/contact details.

### 3. Services page

Replace the current English-only catalogue body with bilingual content driven by the shared content model.

Use the six approved service families:

1. 留学与学生签证 / Study & Student Visa
2. 技术移民与雇主担保 / Skilled Migration & Employer Sponsorship
3. 配偶与家庭类 / Partner & Family
4. 签证拒签与 ART 复审 / Visa Refusal & ART Review
5. 永居与公民相关服务 / Permanent Residence & Citizenship-related Services
6. 复杂案件与个案策略咨询 / Complex Matters & Case Strategy

Service descriptions should be restrained, general and non-guaranteeing.

Do not turn service cards into legal eligibility advice.

### 4. Process page

Create a bilingual service journey around the accepted model:

```text
1. Tell us about your situation
2. AI helps organise the initial information
3. Build a consultation/matter summary
4. Escalate to a lawyer when needed
5. Continue service/follow-up
```

Chinese should be the default display.

Do not imply that AI makes final legal decisions.

### 5. Contact page

Use CTA-first contact design.

Allowed actions include:

- start AI consultation;
- request/contact a lawyer through existing site workflow;
- continue to existing consultation/request paths if available.

Do not invent:

- phone;
- office address;
- email;
- WeChat;
- opening hours;
- consultation price.

If no real scheduling workflow exists yet, do not pretend one exists. Use truthful wording such as “提交咨询需求” / “Request consultation” tied to an existing route or clearly non-final UI action.

### 6. Lawyer/team placeholder section

Provide reusable card structure only if it can remain clearly provisional.

Requirements:

- explicit placeholder/demo marking in both languages;
- generic avatar/visual placeholder;
- no realistic invented certificate/credential data;
- no success statistics;
- no real-person likeness;
- data isolated so future confirmed profiles can replace it centrally.

## Locale behavior

All major visible copy added or materially rewritten in P11-002A must switch with the existing site language control.

Chinese is the default.

Do not create a second locale state.

Do not introduce `/zh` or `/en` route prefixes.

Do not bind site locale to AI answer language.

## Visual scope

Use the existing production component/Tailwind architecture.

P11-002A may improve layout enough to support the new structure, but broad visual-fidelity work is intentionally deferred.
