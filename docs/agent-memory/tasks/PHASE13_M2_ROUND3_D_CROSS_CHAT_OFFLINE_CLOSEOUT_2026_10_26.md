## 2. Implement one shared, server-derived Project resolver

Build a server-only, typed, injectable resolver such as `chatbot/lib/projects/context-resolver.ts` and compose it through existing `resolveWorkspaceContext()` (or a comparably narrow shared before-model seam).

### Identity and authorization

1. Resolve owned `Chat` / `ImmigrationConversation` from authenticated **server session** user ID. Query persisted exact `ProjectConversation` association for this Chat. Standalone has **no association** and retains `projectId:null` and existing Phase 12 conversation-local documents, policy binding, history, matterId and evidence. Never create a Project association for a Standalone/legacy Chat.
2. If Project-associated, verify canonical Project active, registered non-guest customer and **same actor owns this exact Chat** and current owner/active membership. Even a Project owner cannot read another member's private Chat history. Use `authorizeProjectAccess` as real authorization, not `getProjectChatOrigin` alone. Recheck after significant async fetch and immediately before model submission; revoked membership/closure/feature off => block new Project turn fail-closed, not answer as standalone; no silent premium fallback to Default or wider account context.
3. Absent/incomplete Project DB schema or inconsistent association must **not** be interpreted as Standalone when persisted Project origin may exist. Handle schema absent/partial explicitly using existing readiness semantics; preserve permitted standalone behavior. External locator `projectId` is never an authorization credential.
4. Do not change M1's origin-preserving read-only history policy, request-scoped legal Matter, policy topic or per-Chat ConversationTurn execution fencing. No cross-Chat transcript loading. Typed and bounded Project packet only.

### Stable fact packet

5. Use R1-corrected **`stableProjection()`**, not raw `projection()`, and revalidate actor Project membership, assertion creator/publication audience, exact assertion version, current `customer_confirmed` state, active explicit publication and active independently revocable `ai_context` use grant. Exclude stale/superseded, rejected/disputed, unverifiable evidence, person-scoped (unless separately authorized), hidden/private and **all unresolved conflicts, including hidden or possible conflicts**. Never turn candidate/unknown/provisional requirement into stable fact.
6. Serialize explicit scoped provenance: assertion ID + exact version, key, typed value, original `customer_stated` vs extracted origin, effective/observed date if known, statement confirmation attribution, and only allowed source evidence locator; label **customer-stated, NOT government/lawyer independently verified**. Bound fact count, per-value size and total serialized bytes; deterministic ordering/dedupe, no PII diagnostics.
7. `unresolvedCandidates` and conflicting details are NOT included in prompts; they may be available for a separately authorized UI later but must never disclose hidden fact IDs/values. Same Project Chat B can consume a legitimately published/AI-granted creator fact A only if publication audience/permission **explicitly permits that viewer**; otherwise creator-only. Membership alone grants nothing.

A test-only explicitly authorized synthetic fixture may validate happy path; **never manufacture a production grant**. Preserve original Phase12 own-Chat evidence scope separately and do not reclassify it as Project evidence.
