## Typed Policy Intelligence model

Create a small typed model with stable IDs/slugs.

Exact naming is a technical choice, but the semantics must separate at least:

### Source/legal status

A field representing the real status of the source/policy, conceptually such as:

- `in_force`
- `announced`
- `proposed`
- `consultation`
- `superseded`

Do not force every item into only enacted/proposed if the real source state is more specific.

### Editorial publication status

A separate field representing platform workflow, conceptually such as:

- `draft`
- `review_required`
- `published`
- `archived`

Only public/published entries may render on the public list, Home preview, or public detail route.

### Official-source identity

Each publishable entry must have sufficient source identity, including fields conceptually equivalent to:

- authority/source organisation;
- official source title;
- official source URL;
- source publication/announcement date when known;
- effective date when applicable;
- jurisdiction/category.

Do not invent missing official metadata.

### Analysis layers

Keep distinct fields/sections for:

1. **Official source facts / source metadata**
2. **AI-assisted analysis / explanation**
3. **Lawyer commentary**, optional and absent until actually supplied

The model should be compatible with a future `origin: manual | automated` or equivalent discovery field so P11-003B does not require redesigning the public UI.

Do not overengineer a generic CMS.

## Public list page — /intelligence

Build a bilingual public Policy Intelligence stream inspired by V4.

Expected capabilities:

- page title and explanation;
- published items only;
- clear source/legal-status badge;
- date;
- authority/source;
- category;
- concise bilingual summary;
- affected group / practical relevance where manually supplied;
- search over published entries;
- useful status/category filtering if the data model supports it cleanly;
- newest/recent ordering based on real source dates, not fake sync timestamps.

Do not show:

- fake “official source synced at…” status;
- fake number of monitored sources;
- fake real-time update claims.

When there are no published entries, render a high-quality empty state explaining that reviewed policy interpretations will appear after source verification.

## Detail page — /intelligence/[id]

The detail page must make provenance visually obvious.

At minimum separate:

### A. Official source

Show source authority, title, URL, date/status metadata and effective date if actually present.

This section must not contain invented statutory text.

If no verbatim excerpt is supplied in the curated data, do not manufacture one.

### B. AI-assisted analysis

Use the accepted purple AI visual semantics.

Clearly label it as analysis/explanation, not official law and not lawyer advice.

### C. Lawyer commentary

Use amber/gold human-lawyer semantics.

This section is optional.

If no reviewed lawyer commentary exists, show a truthful state such as:

`暂无已发布律师点评`

/ `No lawyer commentary published yet`

Do not invent a lawyer opinion to fill the card.

### D. Practical impact / affected groups

May be displayed only from manually curated fields.

Avoid converting high-level policy descriptions into case-specific eligibility advice.

## Provenance rule

The UI must visibly reinforce:

```text
Official source facts != AI-assisted analysis != Lawyer commentary
```

Also reinforce:

```text
source/legal status != editorial publication status
```

A proposed/consultation item can be published as an explanation, but it must remain visibly proposed/consultation and never appear to be current law.
