Public AWS references checked 2026-10-25:
- GuardDuty Malware Protection publishes S3 object scan results to the EventBridge **default event bus**, fields include `detail.scanStatus`, `detail.s3ObjectDetails.versionId`, plan ARN, account and region: https://docs.aws.amazon.com/guardduty/latest/ug/monitor-with-eventbridge-s3-malware-protection.html
- GuardDuty S3 scanning uses at-least-once events and may emit duplicate scan results: https://docs.aws.amazon.com/guardduty/latest/ug/how-malware-protection-for-s3-gdu-works.html
- S3 Versioning and Object Lock have different deletion/retention semantics: https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html
- EventBridge->SQS generally uses `Principal.Service=events.amazonaws.com` constrained to exact source rule/account; verify actual resources rather than trusting policy JSON alone: https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-use-resource-based.html and https://docs.aws.amazon.com/eventbridge/latest/userguide/cross-service-confused-deputy-prevention.html
- AWS documentation for **new EventBridge V2/custom buses** states that `aws.` event-source prefix is service reserved for `PutEvents`: https://docs.aws.amazon.com/us_en/eventbridge/latest/userguide/eb-custom-bus-addressing.html and https://docs.aws.amazon.com/cli/latest/reference/eventsv2/put-events.html . **Do not generalize this newer API statement as proof that all account buses, forwarding routes, legacy PutEvents, SQS SendMessage, queue resource policies, admin/role control, or cross-account paths are safe.** A blanket claim "any PutEvents caller can impersonate aws.guardduty" is also not supported. Record an **API- and topology-specific** spoofing assessment, distinguish direct-to-SQS spoofing from bus event injection, require measured/officially documented evidence. If unresolved -> NO_GO.
- S3 GetBucketVersioning is read-only and supports ExpectedBucketOwner; Queue GetQueueAttributes, Events DescribeRule/ListTargetsByRule and STS GetCallerIdentity are read-only AWS operations: https://docs.aws.amazon.com/cli/latest/reference/s3api/get-bucket-versioning.html , https://docs.aws.amazon.com/cli/latest/reference/sqs/get-queue-attributes.html , https://docs.aws.amazon.com/cli/latest/reference/events/describe-rule.html , https://docs.aws.amazon.com/cli/latest/reference/sts/get-caller-identity.html .

**Important:** CLI/API read-only is not automatically cost-free. May reveal account infrastructure. Even well-scoped read-only capture needs operator approval for accessing a live account. A generic event payload, a QueueUrl, an SQS receipt/message ID or `source=aws.guardduty` string is NOT authenticated GuardDuty evidence. There is no cryptographic GuardDuty attestation in these modules.

## 3. B2-0 contract for CLI / tested evidence model

Typed operator `scope`: `schema`, `environment:"isolated_sandbox"`, `approvedAccountId`, `region`, `partition`, `awsProfile`, `resourceSelectors` (bucket, guarded project-document prefix `project-document/`, GuardDuty plan ID/ARN, default bus, rule name, queue name/ARN/URL, DLQ ARN, selected application role ARN and optional KMS ARN). Strings validated exactly; no unnamed default for production, no wildcard ARN or credential. If existing resources are not known, output a human checklist of required selectors; no caller profile discovery.

Typed `approval`: task-specific user-authored local record ID, approved identity & exact resources, approval date+finite expiration, `scope:"read_only"`, acknowledgements `nonproduction_only`, `no_mutation`, `no_object_access`, `no_message_consumption`. This is an **operator workflow approval check**, not cryptographic proof of IAM or user identity. Never permit a fixture approval to activate real calls. The script must check account from STS before other calls even with approval.

`plan` outputs a stable ordered request list and estimated upper bound on calls (not dollars), redacted paths, timeout/cancel behavior, inaccessible evidence as `INCOMPLETE`. Explicitly refuse any update/delete/create, `PutEvents`, `SendMessage`, `ReceiveMessage`, `GetObject`, S3 list, `AssumeRole`, `iam:SimulatePrincipalPolicy` where unsupported/approval is absent, and entire PostgreSQL access.

`collect-read-only` uses only syntactically pinned AWS CLI subcommands (or SDK's explicit read-only APIs), and explicit account ID and expected owner. CLI credentials MUST come from named operator-profile with AWS SSO or short-lived read-only credentials; do not create/modify credentials. If AWS CLI missing, incomplete. Command output validated for JSON shape, max-size and timestamp. Stable bounded `NoSuch.../AccessDenied` codes, no stderr secrets.

Use injection for fake command executor in test, record every attempted command; ensure zero non-allowlisted commands, zero calls in plan/tests, STS-first and exact-account stop, short-circuit after auth mismatch, explicit region and owner flags for S3, no lateral discovery. Unit tests must make it impossible to call real AWS during test by using fake only. Include an offline snapshot showing neither evidence nor local approval can ever prove authenticated GuardDuty source; include a separate finding for EventBridge V2 reserved `aws.` source semantics vs classic default bus, direct SQS injection and admin policy mutation, without making unjustified spoofability assumptions.
