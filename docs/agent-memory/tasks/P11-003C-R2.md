## 2. Home Affairs strategy

## 3. Response-size calibration

The fetch cap applies to the DECODED response body.

The known Home Affairs seed is about 1.43 MB decoded, so the previous 128 KB cap is incompatible.

Implement a tightly bounded source/strategy-specific response allowance sufficient for this known page.

Preferred ceiling:

`2 * 1024 * 1024` bytes decoded for the Home Affairs structured-alert seed.

Do not turn this into an unrestricted global 2 MB-per-page crawler.

Keep smaller limits for other strategies when practical.

Retain:

- full-operation deadline from R1;
- total-run byte bound;
- exact host allowlist;
- redirect revalidation;
- DNS/private-network protection;
- max pages/candidates;
- content-type restrictions.

Because this Home Affairs strategy should fetch only the configured seed in R2, bound its page count/fan-out accordingly.

## 4. Structured siteData extraction

Implement deterministic extraction of:

`<script id="siteData" type="application/json">...</script>`

Requirements:

- fail safely if missing;
- fail safely on invalid JSON;
- ensure `alertItems` is an array before processing;
- bound number of alert records examined/emitted;
- bound candidate text/preview length;
- do not execute script content;
- no DOM/browser runtime required.

Do not rely on brittle exact whitespace around attributes if a modest robust parser/regex approach is sufficient.

## 5. Candidate semantics

A Home Affairs alert candidate remains:

`policy-intelligence.discovery-candidate.v1`

unless an additive, backward-compatible raw metadata field genuinely requires a schema version change. Avoid unnecessary schema churn.

Use acquisition/provenance fields only.

Allowed candidate evidence can include, where safely mapped:

- authority;
- configured source ID;
- canonical URL from an alert URL that passes the SAME allowlist/canonicalisation checks;
- raw discovered title;
- bounded raw content/preview;
- retrieval timestamp;
- content fingerprint;
- discovery strategy;
- raw alert metadata such as category/type;
- raw `updateDate` as source metadata.

CRITICAL:

`updateDate` must NOT become automatically:

- effectiveDate;
- commencement date;
- `explicitSourceDate` if that field semantically implies publication/effective date without evidence;
- `PolicySourceStatus`;
- editorial status.

Prefer keeping it explicitly named as raw alert/update metadata.

Do not generate bilingual copy.

Do not add lawyer commentary.

## 6. Alert URL handling

If an alert contains URLs:

- accept only configured allowlisted HTTPS Home Affairs URLs;
- canonicalize using existing security helpers;
- ignore/reject out-of-scope URLs;
- do not fetch those URLs in R2.

If an alert has no usable URL, decide whether it can still be represented as a candidate tied to the seed page. If so, make that provenance explicit and deterministic.

Do not invent a URL.
