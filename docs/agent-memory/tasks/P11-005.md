# P11-005 — Secure Matter Documents & AI File Intake

**Status:** PLANNED / READY — implementation not started  
**Milestone:** Phase 11  
**Planning checkpoint:** `225ce5f3b11f0b7044eaa60cefa7f51d8a89cfa2` (P11-004 closeout HEAD before this roadmap-only rebaseline)  
**Task granularity:** one major task with three internal stages; do not split routine refinement into A/B/C subtasks.

## Goal

Add a production-grade, matter-scoped document capability so customers can securely provide PDF/JPEG/PNG evidence, the system can derive bounded provenance-preserving document content for AI analysis, and authorized human-service workflows can continue with the same document references.

This task is a new security/data boundary. It is not a cosmetic attachment button.

## Why this task now

The matter-centered Client Portal would otherwise be built around incomplete matter continuity.

Current repository facts:

- `Message_v2.attachments` is generic JSON metadata, not a first-class matter-document lifecycle.
- `chatbot/components/multimodal-input.tsx` can call `/api/files/upload`, but the active Phase 11 AI Workspace does not use that path.
- the current generic upload route accepts only JPEG/PNG up to 5 MiB;
- it stores objects through Vercel Blob with `access: "public"`;
- PDF handling, private document authorization, page-level extraction provenance, and matter/lawyer continuity are absent.

Customer immigration files may contain passports, visa decisions, financial records, relationship evidence and other highly sensitive material. Public object URLs are not an acceptable production authorization model.

## Architecture boundary

Production direction:

```text
customer browser
    -> authenticated matter/document API
    -> private object storage (AWS S3 production adapter)
    -> PostgreSQL document metadata/lifecycle

private object
    -> bounded document processor
    -> normalized text / extracted fields / page provenance
    -> explicit selected-document evidence
    -> AI analysis and authorized lawyer handoff
```

File bytes do not belong in PostgreSQL.

Do not expose permanent public object URLs. Storage location/key is internal metadata, not customer authorization.

## First supported file types

Initial allowlist:

- PDF — `application/pdf`
- JPEG — `image/jpeg`
- PNG — `image/png`

Do not silently add DOCX, ZIP, HEIC, executable, archive, office-macro or arbitrary MIME support in P11-005.

Limits must be explicit and tested. Final byte/page limits may be calibrated during Stage 1/2, but must remain bounded.

## Data model direction

P11-005 may propose an additive first-class document record because generic message attachment JSON cannot express the required ownership/lifecycle boundary.

Expected concepts include:

- document ID;
- owning user ID;
- chat ID and/or legal matter ID linkage;
- original display filename;
- server-generated storage key;
- MIME type and byte size;
- SHA-256/integrity identity;
- processing status;
- extraction/provenance status;
- created/updated/deleted timestamps.

Exact schema names are implementation details and must be reviewed against existing DB conventions.

Creating additive migration code may be part of Stage 1 after owner authorization. **Do not apply migrations to any shared, staging or production database without separate explicit authorization.**

## Security invariants

Every implementation stage must preserve:

1. Authentication and ownership checks are server-side.
2. Knowing an object URL/key is never sufficient authorization.
3. Upload/read/download/delete must revalidate access.
4. Use server-generated storage keys; never trust raw filenames as object paths.
5. Validate MIME/content signature, extension policy, byte bounds and page/image bounds where applicable.
6. Treat document bytes/text as untrusted input.
7. Document text can provide evidence but cannot provide system/tool instructions.
8. Parser/vision work must be bounded against decompression/resource abuse.
9. No automatic public sharing.
10. Lawyer access must follow existing authorized service ownership/assignment semantics; P11-005 must not invent broader staff access.
11. Deletion/lifecycle behavior must be explicit and auditable.
12. Do not log sensitive document body text or raw file bytes in normal application logs.

A quarantine/scanning strategy must be defined before P11-005 is considered production-ready. Do not represent an unscanned file as lawyer-safe merely because parsing succeeded.

## Provenance invariant

Customer evidence must remain visibly and structurally distinct from:

```text
customer document evidence
!= official/original law
!= AI analysis
!= lawyer advice
```

Derived text/facts must retain at least document identity and page/location provenance when the source format supports pages.

Do not promote extracted customer statements into verified legal facts without appropriate UI/system qualification.

## Stage 1 — Secure document foundation

Implement only after owner explicitly authorizes Stage 1.

Required result:

- private storage abstraction with AWS S3 as production target;
- deterministic fake/test storage adapter so tests do not require live AWS;
- authenticated matter-document upload;
- first-class document metadata/lifecycle;
- PDF/JPEG/PNG allowlist;
- bounded upload size;
- type/signature/integrity validation;
- server-generated object keys;
- owner-scoped metadata/list/read/download/delete authorization;
- no public object URLs;
- explicit processing states suitable for later extraction;
- tests for cross-user denial and invalid file/type/size cases;
- no document interpretation yet beyond validation/metadata needed for Stage 1.

Stage 1 must not wire uploaded content into legal reasoning or lawyer review yet.

## Stage 2 — Document understanding and provenance

After Stage 1 Git/source/security review:

- native PDF text extraction first when trustworthy embedded text exists;
- scanned-PDF/JPEG/PNG processing through a bounded visual/OCR-capable path only when needed;
- normalized extracted representation;
- page-level/location provenance;
- extraction quality/status/error state;
- bounded page count, rendered pixels, extracted text and runtime;
- document prompt-injection defenses: extracted content is evidence/data, never instructions;
- no silent legal conclusions from extraction;
- deterministic fixtures/tests for native PDF, scanned/image document, malformed input and limits.

Do not make OCR the default for text PDFs.

The exact processor/provider belongs to Stage 2 review; do not couple Stage 1 storage to one extraction vendor.

## Stage 3 — Matter / AI / lawyer integration

After Stage 2 review:

- add matter-scoped document presentation to the active AI/customer journey;
- allow customers to select authorized processed documents for an AI question;
- pass only bounded derived evidence/provenance, not unrestricted raw-file content, into the relevant AI path;
- render customer-document provenance separately from official legal citations;
- preserve current conversation, matter, political gate, answer-mode and lawyer-request contracts;
- carry explicit authorized document references into the human handoff where current lawyer-request ownership permits;
- keep real appointment/calendar functionality out of this task.

Do not claim that a document was lawyer-reviewed unless the existing lawyer workflow establishes that fact.

## Explicit non-goals

P11-005 does not authorize:

- public file hosting;
- arbitrary MIME/file support;
- bulk archival ingestion;
- permanent public URLs;
- external sharing links;
- a generic Dropbox/Drive replacement;
- automatic legal conclusions from uploaded evidence;
- legal-service reasoning redesign;
- Fast / Legal Check / Premium provider-policy changes;
- Phase-6 or ReasoningBank changes;
- Stripe/SES changes;
- booking/calendar work;
- AWS deployment;
- applying DB migrations to shared/staging/production environments without explicit authorization.
